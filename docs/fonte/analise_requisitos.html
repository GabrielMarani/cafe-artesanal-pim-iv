LEVANTAMENTO DE REQUISITOS
Requisitos funcionais
CódigoRequisitoDescrição
Acesso e conta
RF01Efetuar loginO sistema deve permitir que o usuário entre com CPF ou e-mail e senha. Se os dados estiverem corretos e a conta estiver ativa, o sistema abre a sessão de acordo com o perfil (cliente, atendente ou administrador). Em caso de erro, deve informar que as credenciais são inválidas, sem dizer qual dado está errado.
RF02Permitir acesso sem loginO sistema deve permitir que o visitante consulte o cardápio e monte o carrinho sem estar logado. O login só deve ser exigido para finalizar o pedido.
RF03Manter clienteO sistema deve permitir que o cliente crie sua conta informando nome completo, nome social (opcional), CPF, e-mail (opcional), celular (opcional) e senha.
RF04Editar dados pessoaisO sistema deve permitir que o cliente altere nome, nome social, e-mail e celular. O CPF identifica a conta e não pode ser alterado.
RF05Alterar senhaO sistema deve permitir a troca de senha mediante a senha atual. Após a troca, as sessões abertas em outros aparelhos devem ser encerradas.
RF06Manter endereçosO sistema deve permitir que o cliente cadastre, edite, remova e defina um endereço principal. Ao digitar o CEP, o sistema deve preencher rua, bairro, cidade e UF automaticamente (serviço ViaCEP).
RF07Desconectar contaO sistema deve permitir que o usuário saia da conta, encerrando a sessão no aparelho e no servidor.
Cardápio
RF08Consultar produtosO sistema deve mostrar os produtos ativos com imagem, nome, descrição, preço e disponibilidade, indicando produtos em destaque, esgotados e com poucas unidades.
RF09Consultar categoriaO sistema deve permitir filtrar os produtos por categoria, destacando visualmente a categoria selecionada.
RF10Buscar e ordenar produtosO sistema deve permitir buscar produtos pelo nome, descrição ou categoria, sem diferenciar maiúsculas e acentos, e ordenar por categoria, nome ou preço.
Pedidos do cliente
RF11Escolher quantidade de itensO sistema deve permitir adicionar produtos ao carrinho, alterar a quantidade, remover itens e esvaziar o carrinho. A quantidade deve respeitar o estoque disponível.
RF12Listar produtos selecionadosO sistema deve listar os itens do carrinho com quantidade, valor unitário e subtotal, além da taxa de entrega e do total. Ao abrir o carrinho, preços e estoque devem ser conferidos com os dados atuais, avisando sobre itens que ficaram indisponíveis.
RF13Realizar pedidoO sistema deve permitir que o cliente finalize o pedido escolhendo retirada no balcão ou entrega em um endereço cadastrado, a forma de pagamento (Pix, cartão de crédito, cartão de débito ou dinheiro) e uma observação opcional. Os valores devem ser calculados pelo servidor.
RF14Listar pedidos realizadosO sistema deve mostrar os pedidos do cliente com número, data, itens, quantidades, valores, forma de pagamento, endereço e status. Cada pedido deve exibir as etapas e a linha do tempo, atualizadas automaticamente enquanto o pedido estiver em andamento.
RF15Cancelar pedido pelo clienteO sistema deve permitir que o cliente cancele o próprio pedido enquanto ele ainda não começou a ser preparado, informando um motivo opcional.
RF16Confirmar recebimentoO sistema deve permitir que o cliente confirme que recebeu o pedido (entrega) ou que o retirou no balcão, finalizando-o.
Atendimento (atendente e administrador)
RF17Listar pedidos recebidosO sistema deve listar os pedidos para a equipe, com filtro por status e busca por número ou nome do cliente. Cada pedido deve mostrar cliente, telefone, itens, valores, tipo de entrega, endereço, pagamento e observação. A lista deve se atualizar sozinha e avisar quando chegarem pedidos novos.
RF18Atualizar status do pedidoO sistema deve permitir que a equipe avance o pedido pelas etapas: pendente, em preparo, pronto, saiu para entrega e entregue. Pedidos para retirada passam de “pronto” direto para “entregue”.
RF19Cancelar pedido pela equipeO sistema deve permitir que a equipe cancele um pedido informando obrigatoriamente o motivo, que fica visível para o cliente.
RF20Listar histórico geralO sistema deve permitir que a equipe consulte todos os pedidos, inclusive os entregues e cancelados, com a linha do tempo de cada um (quem alterou e quando).
Administração
RF21Cadastrar produtoO sistema deve permitir que o administrador cadastre, edite e desative produtos, informando nome, descrição, preço, categoria, imagem, estoque inicial, estoque mínimo e destaque.
RF22Controlar estoqueO sistema deve permitir registrar entradas e saídas de estoque com motivo. O estoque deve baixar automaticamente quando um pedido é feito e voltar quando ele é cancelado, com alerta para produtos abaixo do estoque mínimo.
RF23Cadastrar categoriaO sistema deve permitir que o administrador cadastre, edite, ordene, desative e exclua categorias. A exclusão só é permitida para categorias sem produtos.
RF24Gerenciar usuáriosO sistema deve permitir que o administrador liste e busque usuários, altere o perfil (cliente, atendente ou administrador) e ative ou desative contas. As mudanças devem valer imediatamente.
RF25Visualizar indicadoresO sistema deve exibir um painel por período (7, 30 ou 90 dias ou datas escolhidas) com faturamento, total de pedidos, ticket médio, cancelamentos, clientes atendidos, novos clientes, vendas por dia, produtos mais vendidos, pedidos por status e estoque baixo, permitindo exportar os dados em CSV.
Aplicativo e acessibilidade
RF26Usar o aplicativo móvelO sistema deve oferecer um aplicativo para Android com cardápio, carrinho, finalização do pedido, acompanhamento dos pedidos e área da conta, usando a mesma API do site.
RF27Consultar cardápio sem conexãoO aplicativo deve guardar o cardápio no aparelho e sincronizar apenas o que mudou desde a última atualização, permitindo consultar os produtos sem internet e avisando quando estiver desconectado.
RF28Ajustar acessibilidadeO site deve permitir aumentar e diminuir a fonte, ativar alto contraste e tema escuro, e traduzir o conteúdo para Libras (VLibras). As preferências devem ficar salvas no navegador.

Requisitos não funcionais

REQUISITOS NÃO FUNCIONAIS
CódigoTipoRequisitoDescrição
RNF01DesempenhoTempo de respostaO sistema deve responder às ações do usuário em até 2 segundos, mesmo com vários acessos simultâneos. Para isso, as listas são paginadas, as consultas usam índices no banco e as respostas são compactadas.
RNF02UsabilidadeUsoA interface deve ser intuitiva, com mensagens claras em português, confirmação antes de ações que não podem ser desfeitas e indicação de carregamento.
RNF03ResponsividadeAdaptaçãoO site deve se adaptar a celulares, tablets e computadores sem rolagem horizontal. O aplicativo deve respeitar o tamanho de fonte e o modo escuro do celular.
RNF04ConfiabilidadeIntegridade de informaçõesOs pedidos devem ser gravados em transação, com preços e totais calculados pelo servidor. O estoque deve ser controlado por triggers e procedures do banco, e alterações simultâneas no mesmo pedido devem ser detectadas para que uma não sobrescreva a outra.
RNF05EscalabilidadeAumento de usoA API não deve guardar estado de sessão no servidor (autenticação por token), permitindo executar várias instâncias. O sistema deve poder ser implantado em containers Docker.
RNF06AcessibilidadeInclusão e acessibilidadeO site deve seguir as diretrizes WCAG 2.1 nível AA: contraste mínimo, navegação completa pelo teclado com foco visível, títulos em ordem, rótulos em todos os campos, avisos falados para leitores de tela e respeito à preferência de movimento reduzido. O aplicativo deve ter rótulos para o TalkBack.
RNF07CompatibilidadeNavegadores e dispositivosO site deve funcionar nos principais navegadores atuais (Chrome, Edge, Firefox e Opera) e o aplicativo no Android. A API deve usar REST e JSON, para atender o site e o aplicativo.
RNF08UsabilidadeAprendizado do usuárioO usuário deve conseguir fazer um pedido em poucos minutos, sem treinamento. A equipe deve conseguir atender um pedido com um clique por etapa.
RNF09SegurançaAutenticação e autorizaçãoO acesso deve usar token JWT válido por 60 minutos, renovado por refresh token de 14 dias que só pode ser usado uma vez. Cada função deve exigir o perfil adequado (cliente, atendente ou administrador), e a desativação da conta deve valer imediatamente.
RNF10SegurançaProteção de dadosAs senhas devem ser guardadas com PBKDF2 (100 mil iterações e sal aleatório). O sistema deve limitar as tentativas de login, proteger contra injeção de código (XSS e SQL injection), enviar cabeçalhos de segurança e não exibir detalhes internos em mensagens de erro.
RNF11LegalPrivacidade (LGPD)O sistema deve coletar apenas os dados necessários para o pedido, informando a finalidade no cadastro. Cada cliente só deve ter acesso aos próprios pedidos e endereços. No aplicativo, os tokens devem ficar no armazenamento seguro do aparelho.
RNF12InclusãoNome socialQuando informado, o nome social deve ser usado em todas as telas e no atendimento, no lugar do nome de registro.
RNF13DisponibilidadeFuncionamento sem internetO aplicativo deve continuar exibindo o cardápio e o carrinho sem conexão. Uma queda de internet não deve encerrar a sessão do usuário.
RNF14RastreabilidadeHistórico e auditoriaO sistema deve registrar automaticamente o histórico de status de cada pedido, as movimentações de estoque e as alterações de preço, com data. O histórico de status e as movimentações de estoque também registram o responsável.
RNF15ManutenibilidadeOrganização e testesO código deve ser organizado em camadas (Domínio, Aplicação, Infraestrutura e API) e ter testes automatizados de unidade, de integração com o banco e do aplicativo, executados em um pipeline de integração contínua.
RNF16OperaçãoMonitoramentoA API deve oferecer um endereço de verificação de saúde (/health) que informe se o banco de dados está acessível, e uma documentação interativa (Swagger) no ambiente de desenvolvimento.
